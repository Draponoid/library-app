# Правила внесения изменений и приёмки

## До изменения

Опишите задачу: проблема, ожидаемое поведение, затронутые сущности и критерий готовности. Проверьте её соответствие ТЗ. Если меняются поля базы или бизнес-правила, сначала обновите описание данных и сценарии приёмки. Перед экспериментами с пользовательской базой создайте резервную копию.

## Обязательные проверки

Из корня проекта после установки зависимостей:

```text
python -m unittest discover -s tests -v
python -m compileall -q app.py setup_local.py tests
```

Если установлен Node.js, дополнительно: `node --check static/app.js`. Node.js для запуска приложения не требуется.

После изменений интерфейса вручную выполните сценарии из `docs/DEMO.md`: вход двух ролей, поиск, выдача, возврат, изменение справочника. Проверьте ширины 1440 и 390 пикселей, клавиатурную навигацию, отсутствие ошибок в консоли. После изменения API обновите `docs/API.md`; после изменения схемы — `schema.sql`, `docs/DATABASE.md` и план миграции существующих данных.

## Запрещённые действия

- Передавать в комплекте `.env`, пароли, сессионные cookie, пользовательскую базу или резервные копии.
- Хранить пароли открытым текстом в таблице пользователей, выводить их в журналы сервера.
- Отключать внешние ключи, уникальный индекс активной выдачи или проверки роли ради прохождения тестов.
- Подставлять пользовательские значения в SQL через форматирование строк; значения передаются параметрами.
- Удалять историю выдач, обходить API прямым редактированием рабочей базы без согласованной задачи.
- Заменять неуспешную проверку формальным результатом «пройдено» или удалять значимый тест без объяснения.
- Включать debug-сервер на общедоступном адресе или изменять конфигурацию чужой установки.

## Порядок приёмки

1. Исполнитель передаёт описание изменения, код, актуальную документацию и результаты проверок.
2. Второй участник воспроизводит запуск в отдельном окружении и проверяет критерии задачи.
3. Обнаруженные дефекты исправляются; затронутые проверки повторяются.
4. Изменение принимается, если тесты успешны, сценарий работает, данные не теряются, права ролей сохранены и секреты отсутствуют.
5. При изменении поведения обновляются VERSION и заметки о выпуске. Решение о приёмке записывается с датой и именем проверяющего.

## Git-процесс

Основная ветка — `master`, `features` зарезервирована для будущей работы. Новую функцию связывайте с задачей и проводите через отдельную ветку и pull request в `master`. До слияния второй участник проверяет код и результаты GitHub Actions. Файлы `.github/workflows/`, Dockerfile, зависимости и тесты требуют отдельного внимания при проверке; нельзя ослаблять проверки ради зелёного результата.

CI запускает тесты, проверку синтаксиса и работающего контейнера. После успешной проверки `master` CD публикует образ в GHCR. Для воспроизведения контейнерного запуска используйте раздел Docker в README. Не публикуйте `.env`, базы, резервные копии и настройки IDE.
