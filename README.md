# Библиотека — лабораторные работы №1–3

**Тема 3.** Московский политех, группа 241-351. Дисциплина: «Методология и практики DevOps». Выполнили: Махров И.М., Крамской И.М. Версия: **0.2.0**.

Приложение ведёт каталог книг, авторов, филиалов, экземпляров и факультетов, регистрирует читателей, выдачи и возвраты. Библиотекарь управляет фондом и смотрит отчёты; читатель ищет книги и видит только собственные выдачи.

## Быстрый запуск в Windows

Нужен Python 3.11 или новее с pip; проверено на Python 3.13.5 и Windows. Распакуйте архив, откройте терминал **в папке library-app**. Интернет нужен для первой установки зависимостей.

```powershell
python setup_local.py
.venv\Scripts\python.exe app.py run
```

Откройте **http://127.0.0.1:5000**. Остановка сервера: Ctrl+C. Если `python` не найден, установите Python с добавлением в PATH либо используйте `py -3` для первой команды.

`python setup_local.py` — единый сценарий установки: создаёт .venv, устанавливает
все закреплённые зависимости из requirements-lock.txt, создаёт .env со случайными
секретами, применяет миграции и заполняет пустую БД демонстрационными данными.
Повторный запуск сохраняет .env и существующие записи. Логины: librarian и reader;
пароли смотрите локально в .env. Сценарий не выводит их в журналы.

Для Linux/macOS первая команда — `python3 setup_local.py`, запуск — `make run`.
PowerShell-сценарий `./start.ps1` выполняет ту же установку и запускает приложение.
Для полного набора проверок требуются GNU Make, Python 3.11+ и Node.js 22+.
Проверено локально: Python 3.13.5 и Node.js 24.13.0; CI: Python 3.13.5 и Node.js 22.

## Лабораторная работа №3

```text
make install
make run
make migrate
make verify
make backup OUTPUT=backups/before-change.sqlite3
make restore BACKUP=backups/before-change.sqlite3 OUTPUT=data/restored.sqlite3
```

`make install` равнозначен `python setup_local.py`. Отдельные проверки:
`make lint`, `make sast`, `make test`, `make mutation`. На Windows без работающего
GNU Make тот же шлюз запускается `.venv\Scripts\python.exe scripts/checks.py verify`.
В Linux CI используется `make verify PYTHON=python` после установки lock-файла.

Новая функция: однократное продление непросроченной выдачи библиотекарем.
Срок увеличивается на LOAN_DAYS от прежней даты; операция сохраняется в аудите.

Полный протокол и соответствие 15 пунктам: [docs/LAB3_REPORT.md](docs/LAB3_REPORT.md).
Отчёты: reports/junit.xml, reports/coverage.xml, reports/coverage/index.html,
reports/bandit.json, reports/mutation.json и reports/verify.json.

## Две серверные ВМ: PostgreSQL и ежедневные копии

Серверная версия использует PostgreSQL на server2 (`192.168.204.21`), приложение
работает на server1 (`192.168.204.20:5000`) в существующей службе `labapp.service`.
Параметры подключения берутся из `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`,
`DB_PASSWORD` в существующем `/etc/labapp/labapp.env`. При заданном `DB_HOST`
приложение использует PostgreSQL; без него локальный запуск использует SQLite.
Миграции PostgreSQL выполняются отдельно администратором, при запуске приложения
изменение схемы не выполняется.

Установка, откат и восстановление описаны в
[docs/SERVER_DEPLOYMENT.md](docs/SERVER_DEPLOYMENT.md). Установщики сначала сохраняют
старые данные и конфигурацию. Ежедневные копии PostgreSQL создаются на server2
в 03:00 и независимо на server1 в 03:15 по московскому времени; для каждого
расписания сохраняются семь последних успешных копий. Команды `make backup`
и `make restore` ниже относятся к локальному SQLite; серверный PostgreSQL
обслуживается скриптом `deploy/postgres_backup.py` и службами systemd.

Полный набор интеграционных тестов PostgreSQL подключается к `make verify`, если
задана `LIBRARY_TEST_POSTGRES_DSN`. Она должна указывать на отдельную тестовую БД
с правом создавать временные схемы и роли. В CI PostgreSQL поднимается отдельной
службой. Тесты не используют адрес и учётные данные рабочей БД.


## Проверка после запуска

1. Откройте `/health`: ожидаются `status: ok`, `database: ok`, `version: 0.2.0`.
2. Войдите как библиотекарь с паролем из `.env`. В каталоге находятся четыре книги и восемь экземпляров.
3. Откройте «Выдачи и возвраты», выберите экземпляр и читателя, оформите выдачу.
4. Примите возврат, затем откройте «Отчёты» и «Журнал действий».
5. Выйдите и войдите как читатель: управление фондом и отчёты недоступны, отображаются только его выдачи.

Полный сценарий защиты: [docs/DEMO.md](docs/DEMO.md).

## Что реализовано

- Веб-интерфейс на русском языке, адаптированный под настольный и мобильный экран.
- Регистрация читателей, вход, выход, серверные сессии с истечением срока, хеширование паролей scrypt.
- HTTP JSON API, SQLite для локального запуска и PostgreSQL для двух серверных ВМ.
- Создание, просмотр, изменение и удаление книг, авторов, филиалов, факультетов и экземпляров.
- Поиск по названию, автору, ISBN/шифру без учёта регистра; фильтры автора, филиала и наличия.
- Выдача на 14 дней; максимум 5 активных выдач; запрет новых выдач при просрочке.
- Защита от двух активных выдач одного экземпляра, в том числе при одновременных запросах.
- Возврат с сохранением истории; запрет повторного возврата и изменения выданного экземпляра.
- Отчёты о фонде, просрочках, популярных книгах и выдачах по факультетам.
- Журнал последних 100 изменений, JSON-ошибки, CSRF-защита, служебный адрес `/health`.
- Команда согласованного резервного копирования SQLite.

У книги один основной автор. Для коллективного авторства модель можно расширить связующей таблицей в следующей версии. Поле `isbn` допускает внутренний шифр; значения `DEMO-001` и т.п. — демонстрационные шифры, не настоящие ISBN. Отчёты вычисляются по данным, отдельной таблицы отчётов нет. Кэширование не требуется в ЛР1 и пока не реализовано.

## Конфигурация

Переменные окружения имеют приоритет над `.env`. Относительный путь базы отсчитывается от папки приложения.

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| SECRET_KEY | обязателен, минимум 32 символа | Секрет конфигурации Flask; сессии хранятся в БД |
| DATABASE_PATH | data/library.sqlite3 | Путь к базе |
| DB_HOST | не задан | Адрес PostgreSQL; включает серверный режим |
| DB_PORT / DB_NAME / DB_USER | 5432 / library / labapp | Параметры PostgreSQL |
| DB_PASSWORD | не задан | Пароль PostgreSQL из серверного EnvironmentFile |
| HOST | 127.0.0.1 | Интерфейс прослушивания |
| PORT | 5000 | HTTP-порт |
| SESSION_HOURS | 8 | Срок сессии, целое положительное число |
| COOKIE_SECURE | false | true только при работе через HTTPS |
| LOAN_DAYS | 14 | Продолжительность выдачи в днях |
| MAX_ACTIVE_LOANS | 5 | Лимит активных выдач читателя |
| DEMO_LIBRARIAN_PASSWORD | задаётся при настройке | Пароль librarian при init-demo |
| DEMO_READER_PASSWORD | задаётся при настройке | Пароль reader при init-demo |

При ручной настройке скопируйте `.env.example` в `.env`, замените ключ и оба пароля, выполните `python app.py init-demo`. Изменение паролей в `.env` **не меняет уже созданные учётные записи**. Для восстановления утраченного доступа в учебной установке можно восстановить сохранённую базу. Интерфейс сброса пароля в версии 0.2.0 не предусмотрен.

## Автоматические проверки

Выполните `make verify`. Порог совокупного покрытия строк и ветвей — 80%, тесты работают с
независимыми временными базами внутри .tmp/. Подробности — в разделе ЛР3 выше.

## Резервная копия и восстановление

```powershell
.venv\Scripts\python.exe app.py backup --output backups/library-2026-09-19.sqlite3
```

Используется SQLite Backup API; допустимо копирование работающей базы. Файл назначения должен быть новым. Для восстановления остановите приложение, выполните `make restore BACKUP=backups/library-2026-09-19.sqlite3 OUTPUT=data/restored.sqlite3`, укажите `DATABASE_PATH=data/restored.sqlite3` в .env и снова запустите приложение. Так не требуется удалять исходную базу или её служебные файлы. Сначала проверьте каталог и `/health`. Копия содержит пользователей, хеши паролей и сессии: храните её с ограниченным доступом. Восстановление возвращает состояние всей базы на момент копирования.

## Git и CI/CD

Публичный репозиторий: https://github.com/Draponoid/library-app.
Основная ветка — `master`. Ветка `features` создана от готового `master` для будущей работы, без отдельных изменений.

Workflow `.github/workflows/ci-cd.yml` запускается при push в `master` и `features`, pull request в `master`, а также вручную. Он устанавливает зависимости, выполняет полный make verify с отчётами, линтером, SAST и мутациями, собирает Docker-образ и проверяет `/health` и главную страницу работающего контейнера. Только успешный запуск для `master` публикует тот же проверенный образ в GHCR:

- `ghcr.io/draponoid/library-app:latest`;
- `ghcr.io/draponoid/library-app:sha-<полный SHA коммита>`.

Публикация использует встроенный `GITHUB_TOKEN`, отдельный пароль реестра не нужен. CD здесь означает доставку образа в реестр; автоматического развёртывания на удалённый сервер нет. Видимость пакета GHCR настраивается отдельно от видимости репозитория; для приватного пакета требуется `docker login ghcr.io` с правом чтения пакетов.

## Docker

Нужен запущенный Docker с поддержкой Linux-контейнеров и Docker Compose. Скопируйте `.env.example` в `.env`, замените `SECRET_KEY` случайной строкой не короче 32 символов и задайте два разных демонстрационных пароля длиной 10–128 символов. `.env` не публикуется в Git и не попадает в образ.

```powershell
# Собрать образ локально
 docker compose build
# Только один раз для нового пустого тома: создать пользователей и демоданные
 docker compose run --rm library python app.py init-demo
# Запустить приложение
 docker compose up -d --no-build
# Проверить состояние и логи
 docker compose ps
 docker compose logs --tail 50
# Остановить, сохранив базу
 docker compose down
```

Откройте http://127.0.0.1:5000. Вход: `librarian` или `reader`, пароль — заданный в `.env`. Вместо локальной сборки можно выполнить `docker compose pull`, чтобы получить опубликованный образ, затем те же команды инициализации и запуска. Повторная инициализация заполненной базы намеренно запрещена.

В контейнере используется Waitress на порту 5000 и непривилегированный пользователь. SQLite хранится в постоянном томе `library-data` по пути `/data/library.sqlite3`. Локальная база из `data/` автоматически в том не переносится. `docker compose down` сохраняет том; **не используйте `down -v`, если данные нужны**. Новый образ не стирает базу. Миграции из migrations/ применяются автоматически; перед обновлением остановите сервер и создайте резервную копию.

Проверка контейнера не заменяет прикладные тесты: обе стадии обязательны. Dockerfile копирует только код, схему, статические файлы и зависимости; пользовательские базы, пароли, IDE и Git-история исключены.
