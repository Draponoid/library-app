## Команды

Из корня library-app:

```text
python setup_local.py
make run
make migrate
make verify
make backup OUTPUT=backups/before-change.sqlite3
make restore BACKUP=backups/before-change.sqlite3 OUTPUT=data/restored.sqlite3
```

После restore остановленный сервер запускается с DATABASE_PATH=data/restored.sqlite3.
Файл назначения должен отсутствовать: существующая БД никогда не перезаписывается.
Копия сохраняет данные и историю миграций. Рабочая база пользователя в экспериментах
не использовалась. Bootstrap проверялся в .tmp/bootstrap-smoke с новой .venv;
для повторяемости пакеты устанавливались из локального набора wheel-файлов,
загруженного по тому же requirements-lock.txt.

## Три последовательных изменения схемы

1. 0001_initial: девять исходных таблиц. Существующая полная схема принимается
   через CREATE TABLE IF NOT EXISTS; демонстрационные данные повторно не создаются.
2. 0002_indexes: четыре индекса, включая уникальность активной выдачи экземпляра.
3. 0003_renewal: renewal_count с DEFAULT 0, NOT NULL и CHECK 0..1. Старая активная
   выдача сохраняет даты и получает нулевой счётчик продлений.

Yoyo сохраняет историю и сериализует применение миграций. Перед обновлением
реальной установки нужна резервная копия. Неизвестная или произвольно изменённая
схема не объявляется поддерживаемой старой версией: тестируется исходная схема ЛР1.

## Эксперимент восстановления

Временная БД проходит миграции; в authors добавляется «Контрольная запись».
Создаётся snapshot; затем выполняется DELETE FROM authors и проверяется COUNT=0.
Restore создаёт отдельную БД: имя снова совпадает с контрольным,
integrity_check возвращает ok, foreign_key_check не возвращает нарушений.
CLI-сценарий повторяет тот же путь через main() с migrate/backup/restore.
Проверки также запрещают перезапись существующего файла и создание результата из
отсутствующей/повреждённой копии; отдельный тест сохраняет данные из WAL.

## Функциональное изменение через шлюз

Добавлено однократное продление активной непросроченной выдачи библиотекарем:
старый due_at + LOAN_DAYS, атомарная запись счётчика и события renew.
До реализации три API-теста получали 404 вместо ожидаемого поведения; отдельный
JavaScript-тест не находил функцию действий. После реализации все сценарии
проверяются полным make verify, включая граничный день и конкурентные запросы.

Мутации: due < today → <=; renewal_count >= 1 → >; удаление запрета возврата;
изменение длительности; разрешение bool как int; ослабление лимита; инверсия роли.
Первый запуск нашёл пробел в unit-тесте bool: диапазон года маскировал ошибку типа.
После добавления проверки True как положительного ID обнаруживаются все 7/7 мутаций.
Это целевая мутационная проверка выбранных правил, не исчерпывающий mutation score
всего приложения. Мутанты запускаются в отдельных копиях исходников; ошибки
сборки/конфигурации не считаются обнаруженной мутацией.

## PostgreSQL и две Ubuntu ВМ

Общая логика приложения проверена с SQLite и PostgreSQL 18.6. Тестовая служба
PostgreSQL работает отдельно от рабочей БД: другой кластер, порт 55432,
индивидуальные тестовые схемы; подключение с Windows идёт через SSH-туннель.
Проверены создание чистой схемы, обновление схемы ЛР2 с данными, повторный запуск
миграций, работа роли без DDL, конкуренция, ограничения выдачи и продление.

На синтетической БД PostgreSQL выполнены настоящий pg_dump и pg_restore.
Контрольные количества всех девяти таблиц и хеши записей совпали с согласованным
снимком. После намеренного удаления журнала из тестовой БД восстановление в
другую БД вернуло две записи журнала и новую учебную книгу. Обе временные БД
удалены после проверки; рабочая БД этим опытом не затрагивалась. Повторное
выполнение deploy/lab3-demo.sql не создаёт дубликатов.

Установщики и расписания описаны в [SERVER_DEPLOYMENT.md](SERVER_DEPLOYMENT.md).
Состояние установки на рабочих ВМ следует проверять отдельно по версии /health,
результатам служб резервирования и журналам установщиков: локальные тесты сами
по себе не подтверждают развёртывание.

После проверки серверного развёртывания добавлена регрессионная проверка прав
резервирования. На отдельной синтетической БД PostgreSQL 18.6 роль с SELECT таблиц
и USAGE последовательностей воспроизводит отказ полного pg_dump. Добавление SELECT
только на восемь ID-последовательностей восстанавливает успешный дамп; повторный
SQL-запуск не добавляет прав, CREATE в public остаётся запрещён. Ошибки pg_dump
теперь классифицируются без вывода исходного stderr. Полный локальный make verify
после этого исправления: 94 Python-теста, 2 JavaScript-теста, покрытие 85,94%,
7 из 7 мутаций обнаружены. Результаты исходного прогона с PostgreSQL сохранены
в reports/postgresql/.
